What it takes off your hands

The slow parts of a cost cleanup, done for you. What is left is the part only you can do: deciding.

  1. Checking every regionOne run

    It reads each region enabled for the account in the same scan, so nothing sits unnoticed in a region nobody opens.

  2. Working out what each leftover costsPriced

    Each finding carries its monthly cost, from the AWS price list, or OpenCost's unit prices in a cluster, and the evidence it rests on.

  3. Writing the cleanup commandsOne script

    The HTML report gives every fix a tick box. Tick the ones you want, watch the saving change, and copy the one script. A fix that cannot be undone is never ticked for you.

  4. Reading the whole list again next timeOnly what is new

    A repeat scan from the same directory compares with the last one and says what is new, what was resolved and what is unchanged.

  5. Remembering to check at allIt tells you

    Let it watch and it posts to Slack or Discord only when something new appears, or deploy one template and it emails you every day it has something. Either way, a check that fails says so too.

How it stays safe

Read-only

It only reads

Every AWS call it makes is a Describe, a List or a Get. A test in the repository fails if the code ever calls anything else. In a cluster, every read is a kubectl get --raw, which can only GET, and the repository ships the least-access role those reads need.

It never runs a command

It prints each fix for you to review and says which ones are permanent. Running them is your decision.

It runs inside your own account

The scan happens in your CloudShell or terminal, with your credentials. There is no CloudPilot server in the path, and the tool sends no telemetry.

It is open source

The code is on GitHub under the AGPL, so you can read exactly what it checks before you run it.

What it finds in a cluster

Kubernetes gives a workload whatever its manifest asks for and never checks whether it needed it. One more command reads the cluster your kubectl points at, with the access you already have, and prints the same kind of statement.

npx @meruapps/cloudpilot kube
  1. Workloads that ask for more than they useReversible

    The request against the busiest five minutes of CPU, and the highest memory, that the cluster's own Prometheus holds. One kubectl set resources per container, with the old values as the way back. A container that has been killed for running out of memory never has its memory lowered.

  2. Volume claims no pod mountsPermanent

    Bound, with no running or pending pod using them.

  3. Volumes left ReleasedPermanent

    The claim was deleted and the volume was kept.

Cluster costs use the OpenCost project's default unit prices unless you give your own, and every one of these findings says the same thing: lowering a request frees capacity, and the money is saved once that lets the cluster run fewer or smaller nodes. When Prometheus holds only a little history the finding says how much it had and its confidence drops, and a container with under five minutes is not judged at all. Not yet for clusters: the daily report below.

Sample report

Add --html report.html and the same scan is saved as a single file. Every fix has a tick box: tick the ones you want, the saving updates as you go, and one button copies the script. Open it, print it, or send it to whoever approves the cleanup.

And when the bill moves, not just the waste

Waste is money that has been going nowhere for a while. A spike is money that started going somewhere yesterday. One more command reads the account's daily cost per service and says which services cost unusually much on the latest complete day, judged against their own earlier days.

npx @meruapps/cloudpilot anomalies

This is the one read AWS charges for: $0.01 a request. Cost Explorer is the only call in the list of reads above that costs anything, and only this command and scan --bill ever make it. anomalies makes a single request, and more only if AWS splits the answer into pages, so the first line of its output, and its --help, say what it costs before anything is read. CloudPilot never spends your money unasked.

A fixed rule decides, and no model is involved: the same days always give the same answer. A service is flagged when the latest complete day stands above the median of the days before it by more than three times their spread — the median absolute deviation, scaled to read like a standard deviation — and by at least a dollar, so pennies never raise an alarm however large the rise looks beside a tiny usual cost. Both numbers are yours to set, with --sensitivity and --min-increase. When every earlier day cost the same there is no spread to measure against, so the day has to clear both the dollar floor and 50% above the median. A service with no cost at all in the earlier days is new spend. The day in progress is never asked for, because a partial day always looks cheap, and with fewer than seven earlier days the command says it has not enough history and flags nothing.

Each service it names comes with the day and what it cost, the usual day it was judged against, the rise a day, and what that rise would add up to over 30 days if every day cost as much as this one — arithmetic on a single day, worded as a condition and never as a forecast. It is as plain about what it cannot see: Cost Explorer can take a day or two to settle, so the last day or two may still change, and a cost that comes round monthly reads as a spike each time. A service whose busy day recurs weekly is not flagged every week: a day must also stand out among the earlier days on its own weekday. --notify posts it to a Slack, Discord or other https webhook, and only when something was flagged; --json prints the figures; and a recorded run replays with no network, no credentials and no charge.

Then let it keep checking

Two ways to stop remembering, and both of them speak up only when there is something to decide: the first run sends the whole list once, a run with nothing new sends nothing at all, and a check that could not run gets a message of its own. Silence always means nothing new.

Into the channel your team already reads. Give a scan --notify and your Slack or Discord webhook and it posts what is new since the last scan, each finding with its monthly cost and whether the fix can be undone; any other HTTPS webhook gets the same thing as JSON. cloudpilot watch does the repeating for you: one foreground process to run in tmux, systemd or a container, scanning every six hours unless you set --every, for the account or, with --kube, for the cluster. The fix commands stay in the report rather than the chat, and the webhook URL is treated as a secret: only its host is ever printed, and it is never written to a saved scan or a report.

npx @meruapps/cloudpilot watch --every 6h --notify https://hooks.slack.com/services/...

Or a daily email, with nothing of yours left running. Deploy one CloudFormation template into your own account and the scan runs on a schedule, daily unless you change it. You get an email only on a day something new appears, and it lists only what is new. It runs in your account with the same read-only access, from a template you can read before you deploy it: a build job, a topic for the email, and one small file in S3 so the next run knows what is new. Nothing it creates can change, stop or delete anything else in the account, and a test in the repository fails if the template's permissions grow beyond that. The template and the steps to deploy it, or to stop it again, are in deploy/.

Questions

Isn't this a one-time cleanup?

The first scan usually finds the most. But waste comes back as a team ships: a volume gets detached, a test instance is left running, a snapshot outlives its volume. CloudPilot is one command, so you can run it again whenever you like, for example before each month's bill. A repeat scan from the same directory compares with the last one and says what is new, what was resolved and what is unchanged, so you read what changed instead of the whole list again; --only-new prints just the new findings. Or let it keep checking and speak up only when something new turns up: cloudpilot watch --notify posts to Slack or Discord, or a deployed template emails you daily.

Do you see my data?

No. CloudPilot runs in your CloudShell or terminal and talks to AWS with your credentials. The results are printed there and nowhere else. It reads the size of your S3 objects but never their contents.

One option changes this, and it is off unless you ask for it: --explain and ask send the findings to the AI provider whose API key you supply, so it can write the summary.

Why not just use AWS's own tools?

You can, and they are good. They are also spread across several consoles: Cost Explorer shows what you spent, while Trusted Advisor and Compute Optimizer suggest changes, and some of their checks need a paid support plan. CloudPilot is one command that puts every finding in one list, each with its evidence, its monthly cost and the exact command to fix it. And because it is open source, you can read what it checks.
